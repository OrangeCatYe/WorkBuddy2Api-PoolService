# 积分中心与选号策略

积分中心回答三个问题：积分什么时候到期、按现在的用法会浪费多少、网关怎样分配请求才能少浪费。

## 数据来源

| 数据 | 来源 | 刷新 |
|---|---|---|
| 余额、积分包明细（数量、到期时间） | 各平台的额度接口（WorkBuddy：每 30 分钟拉一次积分包明细） | 每分钟重算 |
| 消耗速度 | 网关请求日志中每个请求的实际扣费（`usage.credit`） | 实时累计 |

消耗速度只统计经过本网关的请求。如果同一个账号还在 WorkBuddy 客户端里直接使用，那部分消耗看不到，预测会偏悲观（浪费偏多）。

启动时用最近 31 天的请求归档（`data/requests/`）重建消耗账本，重启不丢历史。

## 预测方法

对每个账号：

1. **校正明细**：去掉已过期和已用完的包；明细合计大于实时余额时，差额从最早到期的包扣除（明细刷新滞后，上游按到期先后扣费）；明细合计小于余额时，差额视为不过期余额。
2. **消耗速度**：最近 N 天（默认 7 天）实际扣费 ÷ 观测天数。服务运行不足 N 天时按实际时长折算，至少按 6 小时算，避免短时数据放大过度。
3. **模拟**：按到期先后、匀速消耗，算出每个积分包到期前能用掉多少，剩下的就是浪费。
4. **零浪费速度**：对每个到期时间点 t，计算「t 之前到期的积分合计 ÷ 距 t 天数」，取最大值。
5. 到期时间超过 90 天的包视为长期余额，不计入浪费。

全池另算一个「理想浪费」：把所有账号的积分包合并，假设全池消耗可以随意分配到任何账号。它和各账号浪费之和的差距，就是靠选号策略能挽回的部分。

## 选号策略

策略作用于实现了 `provider.RoutingTunable` 的平台（目前是 WorkBuddy）。它只调整加权抽签的权重，不改变平台原有的冷却、熔断、成本分层、在途限制和防撞号逻辑。

**到期压力**（0～1）：

```
压力 = Σ 积分包余额 × e^(−距到期天数 / 5)，再除以全池最大值
```

只看积分包、不看账号自身的预计浪费。原因是自身浪费取决于账号自己的消耗速度，而速度又会被策略改变，会出现「被优先 → 速度变快 → 浪费消失 → 不再优先」的振荡。

**权重系数**：

| 情形 | 系数 |
|---|---|
| 免费模型（倍率 0） | 1，不消耗积分，交给平台原算法均衡 |
| 收费模型 | 1 + (放大倍数 − 1) × 压力 |
| 高价模型（倍率 ≥ 门槛） | 上一行 × (1 + 压力) |
| 账号今日用量 ≥ 每日上限 | 0.05（其他账号都不可用时仍可兜底） |
| 策略关闭 | 1 |

最终权重 = 平台原算法权重 × 系数。

**余额保底**：低于该值的账号不接收费模型，把余额留给免费模型。0 表示沿用平台自身配置（WorkBuddy 为 `providers.workbuddy.pool.credit_floor`）。

**会话粘性**：同一会话会沿用上次的账号以命中提示词缓存，这类请求不经过加权选号，在回放中标为「会话粘性」。

## 配置

`config.json`：

```json
"credits": {
  "strategy": "waste_first",
  "waste_boost": 4,
  "expensive_rate": 0.5,
  "daily_cap": 0,
  "reserve": 0,
  "burn_window_days": 7
}
```

面板「积分中心 → 选号策略」修改后立即生效并写回配置文件。

## 选号回放

最近 300 次选号保存在内存中，包括候选账号、各自权重、系数、被选中概率和理由。面板每 5 秒刷新。

## 接口

| 接口 | 说明 |
|---|---|
| `GET /api/credits` | 预测快照（全池、30 天日历、各账号及积分包） |
| `POST /api/credits/refresh` | 立即重算 |
| `GET /api/credits/decisions?limit=50` | 选号回放 |
| `PUT /api/credits/strategy` | 修改策略 |

## 新平台接入

在 Provider 上实现 `provider.RoutingTunable` 的三个方法即可接入策略：

- `SetRoutingBias(fn)`：选号时把 `fn(accountID, model)` 乘到候选权重上
- `SetPickObserver(fn)`：每次选号后上报候选与结果
- `SetCreditReserve(n)`：设置余额保底

两个回调可能在 Provider 的锁内被调用，核心层的实现只读缓存，不会回调 Provider。不实现该接口的平台仍会显示积分预测，只是选号不受策略影响。
