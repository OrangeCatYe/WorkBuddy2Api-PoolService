# 提案：账号配置导出与导入回环

日期：2026-10-19　状态：已实现（结论已并入 [REQUIREMENTS.md](../REQUIREMENTS.md) §3.6）

## 背景

账号只能在面板里逐个授权添加，或手工拷贝 `auths/*.json`。换机器、重装、备份、把一部分账号分给另一台实例时，没有面板内的办法，只能进到数据目录里手动挑文件。

「添加账号 → 导入凭证」已经能接收凭证 JSON，缺的是对应的**导出**，以及把两端接成回环。

## 方案

### 导出

- 账号页新增「导出配置」入口：工具栏按钮 + 多选批量栏上的「导出」。打开对话框后可逐个勾选账号，支持搜索、全选当前筛选结果、清空。
- 新增可选能力 `provider.AccountExporter`（能力标识 `export`），没有实现的平台自动不显示入口，沿用现有的能力驱动方式。
- 新增接口 `POST /api/providers/{pid}/export`，请求体 `{"account_ids": [...]}`，返回 `{"count", "missing", "accounts"}`。浏览器把 `accounts` 保存为 `.json` 文件。
- 文件内容是**凭证数组**，每项与 `auths/*.json` 落盘形态完全一致（`{"auth":{...},"account":{...}}`，有设备令牌时带 `device_token`）。

### 导入

- 导入侧**不新增格式**：现有 `import_json` 本来就接收凭证数组，导出文件原样可导入。因此 v1.0.0 之后的任何版本都能导入这份文件，也能被其他读取 `auths/*.json` 的工具使用。
- 导入表单增加「从文件载入」，不必再复制粘贴，并显示载入了几个账号。
- 导入说明文案补充：可导入本面板导出的文件。

### 同 UID 冲突：保留较新的凭证

导入时若池里已有同一 UID，且现有凭证的过期时间不早于导入内容，则**跳过**该账号并在结果里说明。

原因：刷新令牌会轮换，用一份旧导出覆盖较新的凭证，会让账号的刷新令牌失效，只能重新授权。迁移工具（`cmd/migrate`）本来就是这个规则，这里保持一致。导入内容更新（例如重新授权后的新令牌）时照常覆盖。

## 安全

导出文件含登录令牌明文，等同账号密码。

- 接口只走已有的管理密钥鉴权；`admin_key` 为空时**拒绝导出**（空密钥意味着面板对外无鉴权，不能再放出凭证）。
- 响应带 `Cache-Control: no-store`，只用 POST，令牌不进 URL。
- 日志只记录平台与数量，不记录任何令牌。
- 对话框内有显著风险提示。

## 不做

- 不导出运行态（余额、冷却、统计）。导入后会重新拉取余额与积分包，运行态本就应该按新环境重新累积；整体迁移旧版运行态仍用 `cmd/migrate`。
- 不加密导出文件。加密需要口令管理，且会破坏「与 `auths/*.json` 同形态、可被旧版本导入」的兼容性。
- 不导出平台参数与网关配置，本次只处理账号。

## 影响面

| 项 | 影响 |
|---|---|
| `config.json` | 无变化 |
| `auths/` `state.json` | 无变化，仅复用现有落盘序列化 |
| `/v1/models` 与网关协议 | 无变化 |
| 导入行为 | 同 UID 且现有凭证不旧于导入内容时由「覆盖」改为「跳过」 |
| 新增能力 | `Capability: export`，`provider.AccountExporter` |

## 验证

- 导出的每一项能被 `parseImported` 解析，字段与池内凭证一致（令牌、过期时间、域、企业 ID、昵称、设备令牌）。
- 只导出被勾选的账号，保持请求顺序，重复和不存在的 ID 不影响其他账号。
- 「保留较新」判定的边界：现有更新、相等、更旧。
- 接口：未知平台、平台无该能力、空选择、`admin_key` 为空、正常返回与 `no-store`。
- 前端类型检查与构建；用示例数据在浏览器里检查对话框各状态。
